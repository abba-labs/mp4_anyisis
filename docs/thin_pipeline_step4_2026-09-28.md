# 第四轮：分离表格几何与文字识别验证

## 结论与范围
本轮完成候选方案排查和验收检查，不是完成通用工具。生产三模块、主解析引擎和生产依赖均未改变；main和原有Word/Excel未修改。img2table 2.0.0仅在隔离的测试环境安装，当前不作为默认后端。

输入为 MP4/GameViewer_96iLJ4Cokv.mp4 的第60帧，源视频 SHA256 为 9b1edeeeeaad01d3beb33cec0b007e5c40abd5371380ca8131db398a8d16d8b7。只是同一真实画面的受控对比，不是全视频或五份视频的完整验收。

## 新证据
1. 复核上轮 img2table 1.4.2 裁剪结果：名义上36行17列，但包含20个零面积单元格，P21/P23正是其中两处。列数正确不等于结构有效。
2. img2table 2.0.0 不运行OCR直接提取几何：整屏产生18列，源A3落在B3，说明行号栏会混入数据；裁去界面后产生16列。A3/D3/E3/F3边界与人工源框一致，但P21/P23没有有效对应单元格。结构缺口发生在OCR之前。
3. 同一裁剪输入改用原生支持的RapidOCR 3.9.2，实际识别出了两条完整的“sram容量由256KB改为64KB”，置信度均为99（不是准确率）；原生Excel的P21/P23仍为空。缺失是文字与表格结构组装的损失，不是没读到文字。
4. 部分下划线在录屏中紧贴横向网格线，RapidOCR把ITCM_M7_0、0x0000_0000等读为空格分隔。没有按地址或名称规则补写字符，未放宽原内容锚点。

## 后续选择
不继续在同一img2table路径上堆叠特例，不把17列或高OCR置信度当成验收。对于该类浅网格、跨列显示备注的Excel录屏，目前测试组合不合格。下一轮应以相同源位置、字符及边界检查对照另一条成熟原生表格解析链路；只有实际通过后再替换主后端，不增加通用插件平台或多引擎路由。跨屏图表、全文覆盖和Word排版仍未完成，本轮没有声称解决。
